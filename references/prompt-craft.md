# 提示词工艺规则

本文是实现细节的唯一出处。SKILL.md 只写流程与判据，凡涉及"怎么拼、怎么改、什么不能做"都以本文为准。

## 一、为什么按维度拆

173 条模板都是 `【画面主体】，A，B，C…` 的形状，每条 4–7 段。段与段之间是**并列**关系，不是一句话——这意味着每一段都可以单独取用或替换。

拆成六维（外加情绪与画质）之后，能做三件纯文本模板做不到的事：

| 能力 | 例子 |
|---|---|
| 只借一半 | "要宋式的配色和光，但构图用广角" → 取 `CN-01` 的 color + light，构图自己写 |
| 换骨架 | "用赛博朋克的构图和光，但颜色换成莫兰迪" → 主风格 `DG-03`，第二风格 `CO-01` 只覆盖 color |
| 查缺补漏 | 用户只说"高级感"，模型发现缺 composition 与 quality 段，从 `CN-01` 补齐 |

维度取值：`style`（风格标记）、`color`、`composition`、`texture`、`light`、`quality`、`mood`。
`quality` 只有 4 条命中（原文多数条目没写画质词），不必强求补齐。

### 七段模板怎么落到五维骨架上

两种骨架不是竞争关系，是同一句话的两种切法：**七段是库里数据的存储结构，五维是写长句时的叙述顺序**。写短句、走模板时按七段；要写长句、自组一段时按五维，别把两者混着堆。

| 五维（叙述顺序） | 由哪几个维度段供料 | 写的时候注意 |
|---|---|---|
| 1 主体与动作 | 主体句（`-s` 里写的内容），不是模板的一部分 | 先写主体，再让风格接管；主体不写动作，模型会摆成图解姿势 |
| 2 场景与构图 | `composition` + 主体的环境线索（陪体、前景、画幅） | 骨架词（三分/对角/框架）必须出现一次，否则主体会悬在正中 |
| 3 光影与氛围 | `light` | 光位 + 动机光源一起写，详见 `craft-color-light.md` |
| 4 风格与媒介 | `style` + `texture` + `color` | 风格名一次就够；材质词比色词更能定媒介 |
| 5 细节与质量 | `quality` + 落点处的材质细节（`texture` 的一部分） | 收尾语只留一句，堆三句以上会互相稀释 |

换算规则只有两条：

1. **`mood` 不单独占一段**——它落在结尾，是给整句定调的一两个词（"静谧空灵"、"阴郁华丽"）；写进中间会打断叙述。
2. **`color` 与 `light` 是「滤镜」**，换第二风格时只有这两段该被覆盖（见下节叠加规则）；其余维度一旦被覆盖，造型就散了。

判据：写完一段长句后，用五维逐项对照标一遍。缺哪一维补哪一维，不要用形容词去填（"高级感""氛围感"填不进任何一维）。

## 二、叠加规则

1. **默认只叠两个：一个造型风格 + 一个色彩或光影风格。** 这是稳定区间。三个以上会被模型平均，结果"哪个都不像"。
2. **第一个是主风格，给全段；后续风格默认只覆盖 color 与 light。** 因为造型（构图/质感/媒介）一旦冲突，画面会散；而颜色和光是"滤镜"，换掉通常不伤结构。
3. **顺序有意义。** 主体在最前，风格随后，负向词最后。多数模型对前部 token 的响应更强，把主体放前面能避免"风格压过内容"。
4. **同一维度只保留一段。** 两段都写"柔光"会让模型以为是两种光。`../scripts/build_prompt.py` 用"后者覆盖前者"处理，并在输出里说明覆盖了哪段。
5. **色彩类是最好用的第二风格。** `CO` 分类的 13 条（莫兰迪、马卡龙、低饱和…）本身就是纯色彩约束，覆盖上去几乎不产生冲突。

## 三、三条冲突规则

不提供 173×173 的冲突矩阵——那近 2.8 万组没有人验证过，编出来就是假数据。改用三条可解释的规则，命中时给出理由与解法。

| 规则 | 判定依据 | 为什么冲突 | 解法 |
|---|---|---|---|
| 媒介冲突 | `medium` 字段：摄影 vs 绘画/版画/插画/动画；三维 vs 绘画类；数字图形 vs 绘画/摄影 | 两种成像体系，模型会在渲染方式间摇摆，常见"半写实半插画"的塑料感 | 二选一；或在主体里显式分工（"人物实拍质感，背景手绘"） |
| 光影冲突 | 一方要求硬光（硬光/直射/强反差/侧光/逆光），另一方要求柔光（柔光/漫射/均匀光/无影） | 两段光被平均，结果灰扑扑，既不硬也不柔 | 只保留一方光影段（`--dims` 排除 light），另一方只借色彩 |
| 时代冲突 | `CN`/`JP` 古典语汇 vs `DG` 数字语汇 | 直接拼会得到"古建筑贴霓虹"的廉价拼贴 | 说明融合逻辑（材质替换/载体错置/时间叠印），或改用已内置融合的条目（新国风、国潮） |

`medium` 为 `mixed`/`graphic`/`cgi` 的条目不参与媒介冲突判定（它们本来就是混合媒介）。

已验证可叠加的高频组合（白名单，可放心用）：

- 宋式美学 + 莫兰迪色系（东方极简 + 灰调）
- 侘寂风 + 低饱和度（做旧 + 统一色阶）
- 赛博朋克 + 霓虹色（同源，加强光色）
- 新中式 + 暖色调（室内摄影 + 色温统一）
- 电影感 + 浅景深（同属摄影，景深补光）
- 水彩画风 + 粉彩（同属柔调）
- 浮世绘 + 扁平插画（同为平涂线描）
- 吉卜力工作室风格 + 马卡龙色系（动画 + 高明度）

## 四、模型语法差异

**这里不再维护表格**。模型语法以 `../assets/models.json` 为唯一数据源（脚本读它），逐个模型的语法、负向、权重、参数与常见坑见 `models.md`。本节只留两条跨模型原则：

1. **语法体系只有四类**：标签式（SDXL）、自然语句（FLUX / Krea 2 / Z-Image）、JSON 布局（MOSS-Image）、中文结构化（Qwen / 即梦 / 通用）。判断一个陌生模型属于哪类，比记住它的每个参数更重要。
2. **同一段提示词不能跨模型复用**。标签串喂 FLUX、自然长句喂 SDXL，都会掉效果；换模型必须重渲染，而不是改几个词。

**跨语言改写**（中文模板 → 英文）：保留文化专名原形（Song Dynasty、Ukiyo-e、Wabi-sabi、Dunhuang），色彩写成具体色名而不是十六进制（模型对 "celadon / moon white" 的反应比 `#B7D3D6` 稳定），构图词意译而非直译（"横平竖直的理性构图" → "strict orthogonal composition"）。

**翻译由谁做**：脚本不硬猜语义，只在 `translation_todo` 里列出需要英译的段。英文优先模型（`language: en`）由 agent 逐段翻译再投喂，保留专名原形。

## 五、负向词策略

各模型到底收不收负向，以 `../assets/models.json` 里 `negative` 段的 `mode` 为准（`separate` / `inline` / `none` / `ignored` / `flag` / `minimal`）。本节只讲通用取舍。

通用负向：`低清、模糊、畸变、多余手指、过曝、欠曝、塑料感、文字乱码、水印`。

按题材追加：

| 题材 | 追加 |
|---|---|
| 写实/人像 | `插画感、塑料皮肤、过度磨皮、AI 脸` |
| 插画/绘画 | `照片感、3D 渲染感、噪点` |
| 产品 | `变形 logo、错误文字、杂乱背景` |
| 建筑/室内 | `透视错误、比例失真、歪斜地平线` |
| 国风/文物 | `日式元素混入、现代物件穿帮` |

负向词不是越多越好，超过约 15 个会稀释正向描述。

## 六、红线

以下四条不是风格偏好问题，是后果问题。

1. **在世创作者不给名字。** 库里 4 条标了 `living_artist`（`JP-10`、`JP-11`、`JP-12`、`IL-19`）。其模板已剔除人名，只留线条、上色、光影、题材的可观察特征。不要自作主张把人名写回提示词——多数平台对此有明确限制，且涉及人格权。判据名单在 `../assets/living-names.json`（含库外的摄影、电影参照），命中即视为违规，改写时照抄条目里的 `features`。
2. **品牌与 IP 只描述特征，不复现角色。** 迪士尼、皮克斯、吉卜力、宝可梦等是商标与受版权保护的角色库。可以说"圆润的立体卡通造型、大眼、柔和次表面散射"，不能说"画一个皮卡丘"。
3. **宗教与民族题材不做戏谑化处理。** 唐卡、敦煌壁画属宗教与文物保护题材，避免夸张变形、避免与娱乐元素拼贴。
4. **不虚构"权威结论"。** 不提"某某模型实测最佳参数"这类无法复现的说法；平台参数一律标注整理时间。

## 七、什么时候不该用这套库

这套库解决的是"画面该长什么样"。以下需求它帮不上，应直接说明并转交：

- 版式与排版结构（图文混排、信息图布局）——需要版式模板，不是画风
- UI / 网页 / App 界面设计——需要设计系统，不是提示词
- 三维建模图纸、工程图——需要建模规范
- 视频运镜与分镜节奏——需要视频提示词规范
